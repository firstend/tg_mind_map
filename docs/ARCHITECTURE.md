# Архитектура системы «Карта идей»

Система для накопления и структурирования мыслей, идей и обсуждений через Telegram с использованием очередей и ИИ.

---

## 1. Общая схема

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  Telegram Bot   │────▶│  Gateway Server  │────▶│  Message Queue  │
│  (приём голос/  │     │  (приём, валидация,│     │  (Redis/RabbitMQ)│
│   текст от юзера)│     │   в очередь)       │     │                 │
└─────────────────┘     └──────────────────┘     └────────┬────────┘
        ▲                                                   │
        │                                                    ▼
        │             ┌──────────────────────────────────────────────┐
        │             │           Worker Pool (воркеры очереди)      │
        │             │  ┌─────────────────────────────────────────┐ │
        │             │  │ 1. Взять сообщение из очереди            │ │
        │             │  │ 2. ИИ: новая тема / продолжение по карте │ │
        │             │  │ 3. Обобщение → RAG-база                  │ │
        │             │  │ 4. ИИ: ответ пользователю                │ │
        │             │  │ 5. Ответ в очередь ответов               │ │
        │             │  └─────────────────────────────────────────┘ │
        │             └──────────────────────┬───────────────────────┘
        │                                    │
        │             ┌──────────────────────▼───────────────────────┐
        │             │  Reply Queue  →  Sender / Bot API           │
        │             └──────────────────────┬──────────────────────┘
        │                                    │
        └────────────────────────────────────┘
                    (отправка ответа в Telegram)
```

## 2. Компоненты

### 2.1 Telegram Bot (клиентская точка входа)

- **Назначение**: приём голосовых и текстовых сообщений от пользователя.
- **Поведение**: пересылает сырое сообщение на Gateway (webhook или long polling → наш сервер).
- **Реализация**: можно отдельный сервис на Python (python-telegram-bot / aiogram) или логика внутри Gateway.

### 2.2 Gateway Server (вход в систему)

- **Назначение**: единая точка входа с интернета.
- **Функции**:
  - Приём webhook от Telegram (или опрос getUpdates).
  - Валидация (подпись, id бота).
  - Нормализация: голос → текст (можно через Telegram API или свой ASR позже).
  - Формирование задачи и **положивание в очередь входящих сообщений**.
- **Не делает**: обработку ИИ, RAG, ответы — только приём и очередь.

### 2.3 Message Queue (очередь сообщений)

- **Входящая очередь (incoming)**: запросы пользователя (user_id, chat_id, text, voice_file_id, timestamp).
- **Исходящая очередь (outgoing)**: готовые ответы для отправки в Telegram (chat_id, text, optional reply_to_message_id).
- **Рекомендация**: Redis (Bull/BullMQ) или RabbitMQ — оба подходят для задач и повторных попыток.

### 2.4 Worker(s) — обработчики очереди

Одна или несколько программ (процессов), которые:

1. **Берут задачу** из incoming-очереди.
2. **ИИ — классификация/понимание**:
   - Новая тема или продолжение существующей ветки по карте мыслей.
   - При необходимости: извлечение сущностей, тегов.
3. **Обновление графа/карты мыслей** и **RAG**:
   - Сохранение мысли в граф (узлы + связи).
   - Обобщение/суммаризация в RAG-базу (эмбеддинги + текст) для последующего поиска.
4. **ИИ — ответ пользователю**:
   - Универсальный помощник (первый агент): ответ на вопрос, опираясь на RAG и контекст карты.
5. **Постановка ответа** в outgoing-очередь.

Агенты (типы отвечающих) могут быть разными; в начале — один универсальный агент.

### 2.5 Reply Sender (отправка ответов)

- Слушает outgoing-очередь.
- Отправляет сообщения в Telegram Bot API (sendMessage и т.д.).
- Может быть тем же процессом, что и воркер, или отдельным лёгким сервисом.

### 2.6 Хранилища

- **Граф мыслей**: граф тем/узлов и связей (Neo4j, или граф в PostgreSQL, или даже простой граф в памяти/файле на старте).
- **RAG-база**: векторное хранилище (pgvector, Chroma, Qdrant, etc.) + текст для поиска по контексту при генерации ответа.

## 3. Потоки данных

### 3.1 Запрос пользователя (голос/текст)

1. Пользователь отправляет сообщение боту в Telegram.
2. Telegram вызывает webhook нашего Gateway (или Gateway опрашивает getUpdates).
3. Gateway кладёт задачу в **incoming** очередь.
4. Воркер забирает задачу → ИИ (тема/продолжение) → RAG + граф → ИИ (ответ) → **outgoing** очередь.
5. Sender забирает из outgoing и шлёт ответ в Telegram.

### 3.2 Ответ пользователю

Ответ формируется в воркере с помощью ИИ, затем кладётся в outgoing и уходит в Telegram через Sender — единообразно для всех агентов.

---

## 4. Агенты (типы отвечающих)

- **Универсальный помощник (первый агент)**: общий ответ на мысль/вопрос с учётом карты и RAG.
- Позже можно добавить агентов: «только суммаризатор», «только вопросы по карте», «напоминания» и т.д. Выбор агента может быть по метке в очереди или по правилам в воркере.

---

## 5. Технологический стек (рекомендации)

| Компонент        | Варианты |
|------------------|----------|
| Язык             | Python 3.11+ |
| Telegram         | aiogram 3 или python-telegram-bot |
| Gateway          | FastAPI (webhook + health) |
| Очередь          | Redis + BullMQ или RabbitMQ |
| Воркеры          | Отдельный процесс/контейнер на Python |
| ИИ               | OpenAI API / local LLM (Ollama и т.п.) |
| RAG              | pgvector или Qdrant/Chroma + эмбеддинги |
| Граф мыслей      | На старте: SQLite/JSON или Neo4j при росте |
