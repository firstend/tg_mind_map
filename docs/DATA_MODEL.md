# Модель данных: граф мыслей и RAG

## 1. Граф мыслей (Mind Map Graph)

Граф хранит **узлы** (темы/мысли) и **рёбра** (связи: продолжение, уточнение, ответ на вопрос и т.п.). Привязка к пользователю — по `user_id` (у каждого пользователя свой граф или общий граф с фильтром по user_id).

### 1.1 Узел (Node)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | str (UUID или slug) | Уникальный идентификатор узла |
| `user_id` | int | Владелец (Telegram user_id) |
| `content` | str | Текст мысли/темы (нормализованный) |
| `summary` | str, опционально | Краткое обобщение для отображения в карте |
| `source_message_id` | int, опционально | message_id в Telegram (для трассировки) |
| `created_at` | datetime | Время появления |
| `updated_at` | datetime | Последнее изменение (если мысль дообогащалась) |

На старте можно обойтись без `summary` и хранить только `content`; `summary` полезен, когда узлов много и карту показываем компактно.

### 1.2 Ребро (Edge)

| Поле | Тип | Описание |
|------|-----|----------|
| `from_node_id` | str | Узел-источник |
| `to_node_id` | str | Узел-цель |
| `edge_type` | enum | Тип связи (см. ниже) |
| `created_at` | datetime | Время появления связи |

**Типы рёбер (edge_type):**

- `continuation` — продолжение той же темы (новая мысль в той же ветке).
- `new_topic` — новая тема, связанная с родителем (например, ответ ИИ «это новая тема» и создание узла).
- `refinement` — уточнение/детализация предыдущей мысли.
- `question_answer` — узел-вопрос и узел-ответ (если храним их отдельно).

На первом этапе достаточно двух типов: `continuation` и `new_topic`.

### 1.3 Хранение графа

Используется **PostgreSQL**: таблицы `nodes` и `edges`; запросы «последние N узлов пользователя» — простым SQL. Масштабируется на несколько воркеров.

## 2. RAG-хранилище

RAG используется для **поиска релевантного контекста** при генерации ответа: по эмбеддингу запроса пользователя ищем ближайшие чанки, подставляем их в промпт ИИ.

### 2.1 Единица хранения (Chunk / Document)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | str | Уникальный id чанка |
| `user_id` | int | Владелец |
| `text` | str | Текст для поиска (нормализованный/обобщённый) |
| `embedding` | float[] | Вектор эмбеддинга |
| `source_node_id` | str, опционально | Ссылка на узел графа |
| `created_at` | datetime | Время добавления |

Текст в RAG может совпадать с `content` узла или быть кратким обобщением нескольких узлов (суммаризация ветки). Связь `source_node_id` позволяет при ответе показывать «из какой мысли» взят контекст.

### 2.2 Хранение RAG

Используется **pgvector** (расширение PostgreSQL): таблица `chunks` с колонкой `embedding vector(1536)`, индекс HNSW для косинусного поиска. Одна БД для графа и RAG, конкурентная запись, персистентность, масштабирование.

---

## 3. Связь графа и RAG

- **При добавлении мысли**: воркер создаёт/обновляет узел в графе и добавляет в RAG один (или несколько) чанков: например, `content` узла и при желании `summary`. Эмбеддинг считаем для того же текста.
- **При ответе пользователю**: по тексту запроса (и при необходимости по последним узлам пользователя) ищем в RAG топ-k чанков, подставляем в промпт; при желании по `source_node_id` можем подтянуть контекст из графа (соседи, родитель).

---

## 4. Идентификация пользователя и изоляция данных

- Все сущности привязаны к `user_id` (Telegram). Один бот — много пользователей; данные изолированы по `user_id`.
- `chat_id` в текущей реализации совпадает с личным чатом пользователя; для групповых чатов позже можно ввести отдельно `chat_id` и привязку пользователя к чату.
